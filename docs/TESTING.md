## 1. 확인한 범위와 남은 범위

프로젝트 API의 저장·재조회·파일 원본·권한 분리와 주요 편집폼을 검사했고, 실제 브라우저에서 데스크톱 및 390px iframe 폭의 시작·예시 화면을 확인했다. **실제 사용자의 로그인부터 저장·재접속까지의 브라우저 흐름과 배포 환경은 아직 확인하지 않았다.**

아래 통과 결과는 해당 환경·입력·검사에 대한 결과다. 모든 브라우저·모든 파일 형식·모든 장애 상황의 검증 완료나 보안 인증을 뜻하지 않는다. AI 역할 설계 검토와 구현 담당의 실행 결과를 정리한 문서이며, 인간 전문가의 실제 회의나 자문 결과가 아니다.

| 검사 | 결과 | 범위·제한 |
|---|---|---|
| localhost HTTP API 통합 검사 | **105 assertions 통과** | 실제 localhost API 요청과 D1/R2 바인딩 경로, 2개 테스트 신원 사용 |
| 서버 입력 스키마 검사 | **18개 통과** | 작업 중 별도로 실행한 입력·검증 규칙 검사 |

| 편집폼 동작 검사 | **통과** | 입력·금액·근거 조건·편집 보존·저장 대기 검사 |

`105 assertions`는 상태코드·응답 헤더·데이터 등 개별 단언의 수다. 105개의 독립된 사용자 시나리오를 모두 수행했다는 의미는 아니다. 스키마·SQL·폼 검사를 합산해 하나의 전체 사용자 테스트 수로 표현하지 않는다.

## 2. localhost API 통합 검사

검사 스크립트: [`scripts/test-api.mjs`](../scripts/test-api.mjs)

### 실행 조건

- 실행 중인 로컬 프리뷰의 API를 대상으로 한다. 기본 대상은 `http://127.0.0.1:4173`이다.
- 스크립트는 `http`의 `127.0.0.1` 또는 `localhost`만 허용하고, 다른 호스트·리다이렉트로 테스트 신원이 전달되지 않도록 제한한다.
- 두 신원은 로컬 HTTP 검사에 사용하는 실행별 fixture다. 실제 ChatGPT 로그인 성공이나 배포 인증 게이트웨이의 신뢰 경계를 검증하는 절차가 아니다.
- 테스트 앱에 별도의 로그인 우회 기능을 추가하는 방식이 아니다. 운영 사이트에 이 fixture를 보내거나 운영 인증 테스트를 대체하는 용도로 사용하지 않는다.
- 테스트용 프로젝트는 실행별 접두어와 UUID로 구분하고, 종료 시 이번 실행에서 만든 fixture만 정리한다. 정리 실패는 실패 상태로 보고한다.

로컬 프리뷰가 준비된 뒤 실행한다.

```bash
SEOLGYE_TEST_URL=http://127.0.0.1:4173 node scripts/test-api.mjs
```

### 검사 항목

| 구분 | 확인한 동작 | 기대·확인 결과 |
|---|---|---|
| 익명 접근 | 신원 없는 프로젝트 목록 조회 | `401` |
| 외부 Origin | 다른 Origin의 쓰기 요청 | `403`; 프리뷰 게이트웨이가 먼저 거절할 수도 있음 |
| 생성·재조회 | 프로젝트 생성, 소유자 목록과 상세 다시 읽기 | `201`·`200`, 생성 데이터·초기 이력 일치 |
| 입력 의미 | 미정 예산과 명시 금액, 음수 예산·소유자 필드 주입 | 미정은 `null`, 부적합 요청은 `400` |
| 계정별 격리 | 서로 다른 두 신원의 목록·상세·쓰기·삭제 | 상대 프로젝트 미노출 또는 `404` |
| 수정·경합 | 최신 버전 저장, 이전 버전으로 덮어쓰기 시도 | 버전 증가, 이전 버전 `409`, 데이터·이력 추가 오염 없음 |
| 근거 요구 | 근거·메모 없는 확인 완료, 이유 없는 해당 없음 | `400` |
| 요청 크기 | 1 MiB보다 큰 JSON 요청 | `413` |
| 파일 업로드 | 한글 파일명의 원본 텍스트 파일 저장 | 파일명·바이트 길이 유지 |
| 원본 보존 | 다운로드 내용과 입력 바이트·SHA-256 비교 | 동일 |
| 다운로드 응답 | 파일 첨부 반환·MIME 스니핑 방지 | `Content-Disposition: attachment`, `nosniff` 확인 |
| 파일 버전 | 같은 이름의 다른 내용을 다시 업로드 | 서로 다른 파일 ID, 이전·새 원본 모두 유지 |
| 파일 접근 격리 | 상대 신원의 다운로드·업로드 | `404` |
| 파일 형식 | HTML, PNG로 이름만 바꾼 SVG 업로드 | `415` |
| 내보내기 | 프로젝트·수정 이력·파일 목록·체크섬 JSON | 내용 일치, 원본은 별도 다운로드 안내 |
| 내보내기 격리 | 상대 신원의 JSON 내보내기 | `404` |
| 보관·복원 | 보관 상태 저장·다시 진행 상태로 변경 | 목록·상세에서 상태 유지 |
| 삭제 확인 | 틀린 프로젝트 이름·오래된 버전으로 삭제 | 각각 `400`·`409` |
| 영구 삭제 | 정확한 이름·최신 버전으로 삭제 후 조회 | 상세·기존 파일 `404`, 목록에서 제거 |
| 캐시·내부정보 | 개인 응답 캐시 정책과 응답 필드 | 검사 대상 응답의 `no-store`, 소유자 내부 필드·객체 키 미노출 |
| 정리 | 테스트가 만든 프로젝트 정리 | fixture 정리 완료 |

**용량 구분:** 통합 검사에서 확인한 `1 MiB`는 JSON 요청 제한이다. 파일 업로드의 구현상 한도는 `20 MiB`이며, 이 실행 결과를 20 MiB 파일의 경계값·대용량 업로드 검증으로 확대해서 표현하지 않는다.

JSON 내보내기에는 원본 파일 바이트가 들어가지 않는다. 현재 프로젝트·이력·파일 목록·체크섬을 제공하며, 파일 원본은 인증된 자료함 경로에서 각각 내려받는다. ZIP 전체 백업 기능을 검사한 것으로 설명하지 않는다.

## 3. 서버·편집폼 검증

### 서버의 별도 하위 검사

| 대상 | 결과 | 기록 방식 |
|---|---|---|
| [`lib/server/project-validation.ts`](../lib/server/project-validation.ts) | 입력 스키마 검사 18개 통과 | 작업 중 별도 실행 결과; HTTP 통합 검사와 구분 |
| [`lib/server/projects.ts`](../lib/server/projects.ts)의 SQL 동작 | SQLite SQL 검사 14개 통과 | 작업 중 별도 실행 결과; 운영 D1 전체 환경 검사와 구분 |

이 두 하위 검사는 이번 작업의 실행 기록이다. 해당 18개·14개를 재실행하는 별도 테스트 파일이 저장소에 포함됐다고 주장하지 않는다. 지속적으로 재실행할 통합 검사는 `scripts/test-api.mjs`다.

### 중단된 업로드 복구 추가 검사

105 assertions 통합 검사와 별도로 **실제 로컬 D1/R2**에 미완료 업로드 상태를 만들어 아래 두 경로를 확인했다.

| 준비한 상태 | 확인한 처리 |
|---|---|
| `uploading` 상태가 15분 이상 지났고 R2 원본의 크기·저장된 해시 메타데이터가 예약 정보와 일치 | 파일 상태를 `ready`로 복구 |
| `uploading` 상태가 15분 이상 지났으나 R2 원본이 없음 | 원본 내용이 없는 빈 취소 표식을 만들고 파일 상태를 `cancelled`로 처리 |
| 위 상태를 처리한 프로젝트를 삭제 | 프로젝트 삭제 성공, 관련 메타데이터 정리 확인 |

추가 검사 종료 후 테스트 프로젝트의 원본과 테스트 표식도 모두 삭제했다. 이 결과는 위 두 복구 경로와 후속 정리의 검증이며, 모든 네트워크 장애·동시 업로드 순서를 포괄한 검사는 아니다.

### 편집폼 검사

대상: [`components/project-editors.ts`](../components/project-editors.ts)

TypeScript 모듈을 메모리에서 변환하고 `onSubmit`을 호출해 다음 동작을 확인했다. 전용 테스트 파일을 새로 저장한 것은 아니며, 실제 로그인 사용자의 브라우저 폼 제출 검사는 아직 별도다.

- 프로젝트 생성에서 첫 3개 필드만 필수이고, 이름의 앞뒤 공백을 제거한다.
- 금액 공란은 `null`, 직접 입력한 `0`은 `0`으로 유지한다.
- 일반 금액의 음수, 유효하지 않은 날짜, 허용하지 않는 출처 URL을 거부한다.
- 사무소 확인 기록에는 날짜·메모, 완료 할 일에는 자료 또는 메모, 해당 없음에는 이유, 변경 합의 기록에는 근거가 필요하다.
- 생성은 배열에 추가하고 편집은 기존 ID를 유지해 교체한다. 원래 프로젝트 객체를 수정하지 않는다.
- 견적 공통 범위를 수정해도 기존 기타 범위와 해당 ID·금액을 보존한다.
- 변경 비용·기간의 음수 값을 증감 기록으로 허용한다.
- 계약의 기존 확인 항목과 다른 프로젝트 자료, 메모의 생성일을 유지한다.
- 질문을 폼에 미리 넣을 수 있으며 저장 시 질문 유형을 유지한다.
- 저장 Promise가 완료되기 전에 제출 처리가 완료된 것으로 반환하지 않는다.

검사 이후 ID 생성은 아래 브라우저 QA에서 확인한 HTTP 환경 문제에 맞춰 공통 `newId`를 사용하도록 변경했다. 이 변경 후 전체 TypeScript 검사는 통과했으며 예시 화면 동작을 다시 확인했다.

## 4. 실제 브라우저 QA

로컬 프리뷰를 실제 브라우저에서 열어 확인했다. 화면 폭 검사는 데스크톱과 **390px iframe**으로 수행했으며, 실제 휴대전화·여러 운영체제 전체의 검증을 뜻하지 않는다.

| 화면·동작 | 확인 결과 |
|---|---|
| 시작 화면 | 주요 문구·로그인 진입·예시 진입 영역 표시 확인 |
| 예시 대시보드 | 읽기 전용·가상 자료 표시, 현재 단계·다음 할 일·요약 확인 |
| 탐색·사무소 | 메뉴 이동과 사무소 비교 화면 표시 확인 |
| 가이드 | 검색어 `측량`으로 조회하고 관련 안내 펼침 확인 |
| 모바일 메뉴 | 390px 폭에서 메뉴 열기·닫기와 탐색 확인 |
| 마무리 | 행정 처리·자료 인수·남은 작업과 보수의 3개 영역 분리 확인 |

### 발견해 수정한 문제

| 문제 | 수정 | 확인 범위 |
|---|---|---|
| 기본 HTTP 프리뷰에서 `crypto.randomUUID` 사용 불가로 예시 생성 오류 | [`lib/id.ts`](../lib/id.ts)의 `newId`에서 `randomUUID`가 없을 때 `crypto.getRandomValues` 기반 UUID 생성 | 변경 후 예시 화면 동작 확인 |
| 닫힌 모바일 오프캔버스의 숨김 상태가 충분하지 않음 | 닫힘 상태의 `visibility` 처리 개선 | 390px 메뉴 표시·숨김 재확인 |

실제 로그인 완료, 로그인 계정의 생성·저장·업로드 UI, 브라우저 저장 실패 재시도, 로그아웃 후 복구는 이 브라우저 QA에 포함되지 않았다.

## 5. 정적 검사와 빌드

| 항목 | 상태 | 남은 조건 |
|---|---|---|
| 편집폼 ESLint | 통과 | 전체 저장소의 모든 lint 규칙 통과로 확대하지 않음 |
| 최종 전체 TypeScript 검사 | 통과 | 후속 변경을 반영한 릴리스 직전 실행 exit 0 |
| 1차 production build | 통과 | 빌드 이후 ID·모바일 처리 등 변경이 있음 |
| 최종 production build | 통과 | 공식 Sites `build-site.mjs`로 후속 변경을 포함한 최종 산출물 생성 |

프로젝트의 pnpm 기준 검사·빌드 명령은 다음과 같다.

```bash
pnpm exec tsc --noEmit --incremental false --pretty false
pnpm build
```

이번 최종 검사는 설치된 TypeScript 실행 파일을 직접 호출한 `node node_modules/typescript/bin/tsc --noEmit --incremental false --pretty false`의 exit 0으로 확인했다. 최종 배포용 빌드는 공식 Sites helper `build-site.mjs`를 사용했다. 일반 개발용 `pnpm build`와 배포 helper 실행을 구분한다.

최종 산출물에는 `/`, `/demo`, `/api/projects`, `/api/projects/[id]`, `/api/projects/[id]/files`, `/api/projects/[id]/files/[fileId]`, `/api/projects/[id]/export` 경로가 있다. 임시 화면 검사 경로 `responsive-check`는 포함되지 않았다.

빌드 성공은 로그인·API·운영 권한 검사의 대체가 아니다. localhost API 통과, 최종 아티팩트 생성, 운영 배포 성공도 각각 별도 결과로 기록한다.

## 6. 배포 후 확인할 항목
